# 자원 조건을 맞춘 격리 실험

`bench/compare`는 같은 호스트에서 독립된 런타임 프로세스와 앱 프로세스를 실행해 A/B/C를 비교한다. 특정 업무를 전제하지 않으며 `/healthy`와 `/fault`는 이번 실험의 보호 대상·장애 대상 역할이다.

## 비교 조건

| 비교군 | 요청 예산 | 앱 프로세스 |
| --- | --- | --- |
| A | 두 경로가 실행 4 + 대기 8 공유 | 4개 공유 |
| B | 경로마다 실행 2 + 대기 4 | 동일한 4개 공유 |
| C | 경로마다 실행 2 + 대기 4 | 서로 다른 2개씩 |

모든 비교군의 총 앱 프로세스는 4개, 실행 예산은 4, 대기 예산은 8이다. 시작 시 생성한 설정에서 이 합계를 확인하며 다르면 실험을 중단한다. 앱 내부 작업 한도는 프로세스당 1, 기본 응답 지연은 5ms, 게이트웨이 큐 예산은 100ms, 전체 요청 예산은 2s다. 서로 다른 비교군을 동시에 실행하지 않는다.

앱 수명 관리는 부하 생성기 안의 동일한 Supervisor가 담당하며, 외부 런타임은 모든 비교군에서 정적 HTTP upstream을 사용한다. 이렇게 하면 관리 방식 변경 대신 예산 공유와 프로세스 공유의 차이를 비교할 수 있다. 정적 upstream readiness는 설정하지 않는다. 재시작 중인 포트의 연결 실패도 결과에 포함한다. 관리형 런타임의 전체 시작·종료 동작은 별도의 `scripts/smoke.sh`와 프로세스 통합 테스트가 검증한다.

각 그룹의 upstream 선택·연결 풀·진행 수 집계는 독립적이다. B는 실제 서버를 공유하지만 두 그룹의 least-active 선택 상태까지 공유하지 않는다. 따라서 A→B의 차이를 순수한 동시 요청 한도 효과로만 해석하면 안 된다. 그룹 분리와 함께 라우팅 상태도 나뉘며 두 그룹이 같은 바쁜 프로세스를 선택할 수 있다. 이 점은 원자료의 정상 단계에서도 확인해야 한다.

## 실행

Linux/WSL2에서 저장소 루트 기준:

```sh
go build -o bin/demo-app ./examples/demo-app
go build -o bin/isolatex ./cmd/isolatex
go build -o bin/compare ./bench/compare
bin/compare -scenario delay -out .tools/delay.json
bin/compare -scenario crash -out .tools/crash.json
```

각 명령은 앞 명령이 끝난 뒤 실행한다. 기본값은 준비 2s → 정상 5s → 장애 5s → 회복 5s이며 A/B/C 순서를 seed 42로 섞어 세 번 반복한다. 각 역할의 목표 도착률은 초당 40회다. 매 trial마다 새 프로세스와 동적으로 예약한 loopback 포트를 사용한다. 종료 시 런타임·앱을 회수하고 직접 만든 임시 폴더를 정리한다.

더 긴 표본을 모으려면 다음처럼 지정한다. 이는 장시간 실행되는 로컬 부하 실험이다.

```sh
bin/compare -scenario delay -warmup 30s -baseline 60s -fault 60s -recovery 60s -repeats 5 -out .tools/delay-long.json
```

Windows에서는 `.exe` 이름으로 세 실행 파일을 빌드한 뒤 `./bin/compare.exe`를 실행한다. 경로 인자는 PowerShell에서도 `-out .tools/result.json`처럼 별도 인자로 전달한다. 네이티브 Windows 실행은 기존 개발 모드의 직접 자식 종료 범위를 따른다.

## 장애와 부하 생성

`delay`는 장애 단계에만 fault 역할 요청마다 1s 지연을 지정한다. `crash`는 장애 단계에서 초당 한 번 POST에 `crash=1`을 지정하며 나머지 fault 역할 요청은 기본 GET 응답이다. 앱이 실제로 종료되고 Supervisor가 재시작한다. 응답 없이 연결이 닫힌 GET을 HTTP 전송 계층이 재시도할 수 있으므로, 크래시 주입에는 자동 재전송 대상이 아닌 POST를 사용한다. 일반 HTTP 5xx 주입이나 CPU·DB 경합 실험은 이 두 시나리오에 포함하지 않는다.

도착 시간은 응답 완료와 무관하게 일정 간격으로 예약한다. 생성기가 100ms 이상 뒤처지거나 진행 요청 256개 한도에 도달하면 해당 예약을 생성 누락으로 집계한다. 목표 예약 수·실제 전송 수·누락·평균/최대 스케줄 지연을 함께 보고하며, 서버가 느려질 때 요청 생성도 줄어드는 현상을 숨기지 않는다.

단계 사이에는 진행 요청을 drain하지 않는다. 장애 단계의 작업이 회복 단계에 남는 현상도 관측한다. 통계는 **요청 시작 단계의 cohort**로 집계하며 응답이 다음 단계에 도착해도 시작 단계에 포함한다. 단계별 전송률은 해당 단계의 길이로 나눈 전송 요청 수다.

## 결과 해석

JSON은 실행 OS/아키텍처·Go 버전·논리 CPU 수·GOMAXPROCS, 두 실행 파일의 SHA-256, seed·도착률, 실행 순서와 trial별 자원 합계를 기록한다.

`load_contract.crash_method`는 현재 `POST`다. 이 필드가 없는 초기 크래시 원자료는 GET 주입 기록이며 자동 재전송 가능성을 통제하지 않았다. 그 결과를 현재 POST 실험과 동일한 주입 조건으로 합산하지 않는다. 원자료는 변경하지 않고 결과 기록에서 구분한다. `sent`는 생성기가 보낸 논리 요청 수이며 모든 전송 계층의 TCP 연결 시도 횟수는 아니다. 재전송 조건은 [Go HTTP Transport 문서](https://pkg.go.dev/net/http#Transport)를 참고한다.

- `scheduled = sent + generator_missed`로 부하 생성 누락을 확인한다.
- `statuses`는 HTTP 상태별 개수이며 `transport_errors`를 따로 기록한다. 둘의 합은 전송 수다.
- `success_ratio_of_sent`는 실제 전송 요청 중 2xx 비율이다. 생성 누락이 있으면 목표 부하를 달성한 실험으로 해석하지 않는다.
- `successful_latency_ms`의 P50/P95/P99는 성공 응답만 포함하며 nearest-rank 방식으로 계산한다. 성공이 없으면 필드를 생략한다. 빠른 503을 성공 지연시간에 섞지 않는다.
- `protected_pids_unchanged`는 보호 영역의 앱 PID 집합을 시작과 끝에 비교한다. A/B에서는 공유 프로세스 4개 전체, C에서는 보호 전용 프로세스 2개다. 요청 성공률과 함께 읽어야 한다.
- `fault_worker_restarts`는 trial 시작과 종료 사이 장애 대상 풀의 재시작 수 증가다. A/B는 공유 풀, C는 장애 전용 풀을 관측한다. 크래시 시나리오에서 이 값이 0이면 장애 실행을 확인하지 못한 것으로 보고 실험을 오류로 종료한다. 포화로 주입 요청이 모두 거절되면 부하를 줄이거나 장애·회복 시간을 늘려 재실행한다. 이 수치는 서버에서 실행한 크래시 요청의 정확한 횟수나 모든 재시작의 원인을 보장하지 않는다.

짧은 실행은 도구·설정·장애 주입을 검증하는 기능 검사다. 성능 결론을 내릴 때는 충분한 준비·측정 시간, 반복별 원자료, 동일한 머신과 빌드, 실제 전송률, 호스트의 다른 부하를 함께 기록한다. 서로 다른 운영체제의 숫자나 소수 성공 표본의 P99를 직접 비교하지 않는다. 프로세스 분리 전후 결과가 호스트 CPU·메모리·공유 DB 격리를 입증하지는 않는다.

2026-10-24의 짧은 로컬 실행 원자료와 해석은 `bench/results/README.md`에 있다. 배포 묶음에는 런타임·데모를 포함하며 비교 도구와 원자료는 소스 저장소에서 사용한다.
