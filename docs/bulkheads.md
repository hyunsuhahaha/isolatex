# 경로별 요청·프로세스 격벽

IsolateX의 목표는 **장애가 발생한 영역의 영향을 가두고 나머지 영역의 동작을 유지**하는 것이다. 사용자가 격리 그룹을 정의하며, 현재 HTTP 구현은 경로별로 받을 수 있는 요청 수와 실행할 프로세스를 따로 배정한다. 그룹은 특정 업무나 의존성 종류에 종속되지 않는다.

alpha와 beta는 동등한 격리 그룹의 예시다. `/b`의 지연·포화·프로세스 크래시가 `/a`에 배정한 용량을 소모하지 않아야 하며 반대 방향도 같은 계약을 따른다.

## 요청 용량을 미리 예약한다

기존 구현에는 그룹별 gate 앞에 전역 선착순 semaphore가 있었다. 예를 들어 전역 한도가 6인데 beta가 실행 2 + 대기 4를 점유하면, alpha 그룹의 gate가 비어 있어도 alpha 요청은 `global_full`로 거절됐다. 그룹별 상한만으로는 다른 그룹의 자리를 보장하지 못했다.

현재 계약은 다음과 같다.

```text
각 그룹의 예약량 = max_concurrent + queue_size
모든 그룹의 예약량 합 <= max_admitted_requests
```

합계를 초과하면 워커나 리스너를 시작하기 전에 설정 오류로 거부한다. 요청은 해당 그룹의 gate에서만 실행 슬롯 또는 FIFO 대기열 자리를 얻는다. 전역 semaphore는 사용하지 않는다. 따라서 활성·대기 요청의 합계는 그룹별 한도와 전역 상한 안에 머물며, beta가 alpha 그룹의 예약량을 차지할 수 없다.

기본 설정의 예:

| 그룹 | 경로 | 실행 | 대기 | 예약량 | 앱 프로세스 |
| --- | --- | ---: | ---: | ---: | ---: |
| alpha | `/a` | 8 | 8 | 16 | 2 |
| beta | `/b` | 2 | 4 | 6 | 2 |
| 합계 | | 10 | 12 | 22 | 4 |

beta의 6자리가 모두 찬 상태에서도 alpha 그룹은 자신의 16자리를 사용할 수 있다. 전역 상한을 32로 올려도 beta의 예약량은 6 그대로다. 남는 10자리는 자동 대여하지 않는다. `queue_size: 0`은 실행 슬롯이 없을 때 즉시 503을 반환한다.

기존에 전역 상한을 그룹별 예약량 합계보다 작게 설정했다면 이제 시작에 실패한다. 전역 상한을 합계 이상으로 올리거나 각 그룹의 실행·대기 한도를 줄여야 한다. `global_full` 거절은 제거했고 그룹 포화는 `queue_full`로 관측한다.

## 프로세스도 독립적으로 배정한다

관리형 `process` 그룹은 각자 별도의 자식 프로세스를 실행한다. 같은 앱 실행 파일을 사용해도 그룹 사이 PID·힙·GC·재시작 예산은 분리된다. 워커 선택과 HTTP 연결 풀도 그룹별이다. 어느 그룹의 준비된 워커가 없어지면 해당 그룹의 요청만 거절하며 다른 그룹으로 넘기지 않는다.

`upstreams`를 설정하면 이미 실행 중인 서버를 사용한다. 두 그룹에 같은 서버를 등록하면 요청 수용 예산은 나뉘지만 그 서버의 프로세스 크래시는 공유한다. 프로세스 격리가 목적이라면 관리형 그룹 또는 서로 다른 외부 서버 프로세스를 사용해야 한다.

전체 앱을 여러 번 실행하므로 스케줄러·마이그레이션·인메모리 상태·DB 연결 풀의 중복 실행 문제는 앱에서 처리해야 한다. 요청 타임아웃이 취소를 무시하는 앱 내부 작업까지 끝내 주지는 않는다. CPU·호스트 메모리·공유 DB 경합은 이 격벽의 보장 범위에 포함되지 않는다.

## 검증과 다음 작업

```sh
go test ./internal/config -run TestAdmissionBudget -count=1
go test ./internal/gateway -run 'TestBulkheadsRetain|TestSaturatedFaultGroup|TestNoReadyWorker' -count=1
go test ./internal/supervisor -count=1 -timeout=90s
go test -race ./... -count=1 -timeout=90s
```

설정 검사는 정확히 맞는 예산, 부족한 예산, 여러 그룹의 합계, 기본 상한 초과, 정수 오버플로를 확인한다. 실제 HTTP 검사는 한 그룹의 실행·대기열을 채운 후 초과 요청 32개와 다른 그룹의 요청을 함께 보내며 다른 그룹의 실행·대기 자리가 유지되는지 확인한다. 전역 여유가 있을 때도 그룹 상한을 넘지 않는지, 완료 후 슬롯이 모두 회수되는지도 확인한다. 통합 테스트는 실제 자식 프로세스를 종료하고 해당 워커의 재시작과 다른 그룹의 PID 유지를 확인한다. CLI smoke는 alpha와 beta를 번갈아 장애 대상으로 삼는다.

이 검증은 용량·장애 전파에 대한 기능 검사다. 운영 부하에서 P95가 유지된다는 성능 보장은 아니다. 개발은 장애 유형과 대상 그룹을 바꿔 격리 계약을 검증하고 남은 공유 장애 지점을 줄이는 기준으로 진행한다. 자원 조건을 맞춘 A/B/C 비교 실험에서는 총 프로세스 수·요청 예산·부하를 고정해 요청 예산 분리와 프로세스 분리의 효과를 각각 측정한다. Circuit Breaker와 Health Check는 이 핵심 계약을 보조한다.
