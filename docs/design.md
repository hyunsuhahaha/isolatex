# IsolateX 설계

## 목적

IsolateX는 장애의 영향 범위를 제한하는 범용 격벽(Bulkhead) 오픈소스다. 서로 독립적으로 유지해야 하는 작업을 그룹으로 나누고, 한 그룹의 지연·과부하·실패가 다른 그룹에 전파되는 경로를 줄인다. 그룹은 기능, 작업 유형, 의존성 등의 경계에 맞춰 사용자가 정의한다.

설계의 판단 기준은 세 가지다.

1. 어떤 장애를 어느 경계 안에 가둘 수 있는가?
2. 해당 그룹에 장애가 발생해도 다른 그룹의 용량과 프로세스가 유지되는가?
3. 공유 자원 때문에 남는 장애 전파 경로를 명시하고 재현할 수 있는가?

특정 업무 시스템은 제품의 전제가 아니다. alpha와 beta 같은 예시 그룹에 어느 쪽으로든 장애를 주입해 동일한 계약을 검증한다.

## 현재 구현의 격리 경계

현재 실행 방식은 단일 호스트 HTTP 런타임이다. 경로를 그룹에 매핑하고, 각 그룹이 자체 실행·대기 예산과 워커 풀을 갖는다. 동일 앱의 여러 인스턴스 또는 그룹마다 다른 앱 실행 명령을 사용할 수 있다.

| 경계 | 구현 | 장애 발생 시 처리 |
| --- | --- | --- |
| TCP 연결 | 공용 리스너 수용 상한·독립 관리 연결 예산 | 포화 시 새 연결 수용 대기, 관리 포트 별도 유지 |
| 요청 수용 | 그룹별 실행 슬롯과 유한 FIFO 큐 | 초과 요청은 해당 그룹에서 거부 |
| 시간 | 큐 대기부터 응답 전달까지 요청 예산 | 마감 시 전달 취소, 슬롯 회수 |
| 프로세스 | 관리형 그룹별 자식 프로세스 풀 | 해당 워커 재시작, 다른 그룹으로 우회하지 않음 |
| 가용성 | 워커별 준비 상태 검사 | 실패한 워커 제외, 연속 성공 시 복귀 |
| 반복 실패 | 선택적 그룹별 Circuit Breaker | 해당 그룹만 차단하고 단일 시험 요청으로 복구 |
| 관측 | 그룹별 상태와 고정 결과 코드 지표 | 어느 경계가 포화·실패했는지 노출 |

용량은 시작 시 예약한다. 모든 그룹의 `max_concurrent + queue_size` 합이 `max_admitted_requests` 이하여야 한다. 요청 처리 중에 전역 슬롯을 선착순으로 나눠 쓰지 않고 다른 그룹의 여유 용량을 빌리지 않는다. 자세한 계약과 설정 호환성은 [bulkheads.md](bulkheads.md)에 있다.

TCP 연결 한도는 경로를 읽기 전의 공용 자원 경계다. 한 경로의 클라이언트가 공용 연결 예산 전체를 점유하면 다른 경로의 새 연결도 대기한다. 그룹별 요청 슬롯 예약과 다른 보장이며, 외부 프록시의 연결·속도 제한이 필요하다. [연결 운영 문서](connection-limits.md)를 참고한다.

`upstreams`로 같은 외부 서버를 여러 그룹에 등록하면 요청 수용 예산은 나뉘지만 프로세스 장애는 공유된다. 프로세스 격리가 필요하면 별도 서버 프로세스를 배정해야 한다. 앱 내부 함수·작업의 자동 분할은 현재 구현에 없다.

## 남는 장애 전파 경로

게이트웨이와 Supervisor는 하나의 런타임 프로세스다. 런타임 자체가 종료되거나 호스트가 실패하면 모든 그룹에 영향을 줄 수 있다. 프로세스 분리는 힙·GC·크래시 경계를 만들며 Linux·Windows에서는 선택적으로 워커 트리의 메모리 상한을 강제한다. [메모리 예산](memory-limits.md)은 호스트 RAM 예약이 아니며 선택적 [CPU 상한](cpu-limits.md)을 지원한다. 공유 DB의 락·연결 경합은 앱과 운영 환경에서 별도로 다뤄야 한다.

타임아웃은 프록시 요청을 취소한다. 취소를 무시하는 앱 내부 작업까지 종료시키지는 않는다. 여러 요청을 처리하는 워커를 요청 하나의 타임아웃 때문에 종료하지 않는다.

운영 헬스체크도 격리 경계를 따라야 한다. `/healthz`는 런타임 생존, `/readyz`는 전체 그룹의 준비 여부, `/readyz/{group}`는 해당 그룹의 준비 여부다. 한 그룹의 장애를 전체 게이트웨이 제거로 확대하지 않도록 경로별 외부 헬스체크는 해당 그룹에 연결한다. 준비 상태는 워커 존재·drain 여부를 나타내며 처리 용량이나 요청 성공 보장과는 별도로 해석한다.

이 경계들을 숨기면 격벽을 실제보다 강하게 주장하게 된다. 새 기능을 추가할 때는 줄어드는 장애 전파 경로와 새로 생기는 공유 자원을 함께 설명한다.

## 검증 방향

각 그룹을 번갈아 장애 대상으로 삼는다. 지연·포화, 요청 취소·시간 초과, 워커 크래시, 준비 상태 실패·회복, 재시작 예산 소진, 종료 중 요청을 검증한다. 성공 조건은 다른 그룹의 요청 수용 예산·워커 PID·준비 상태 유지와 종료 후 슬롯·프로세스 회수다.

성능 비교는 같은 총 프로세스 수·실행/대기 예산·부하에서 수행한다.

- A: 요청 예산과 프로세스 풀 공유.
- B: 요청 예산만 분리하고 프로세스 풀 공유.
- C: 요청 예산과 프로세스 풀 모두 분리.

A→B에서 요청 수용 격리의 효과를, B→C에서 프로세스 장애 격리의 효과를 측정한다. 성공·거절·실패의 지연시간과 비율을 분리해 보고한다. CPU·DB 공유 자원 실험은 별도로 측정해 한계를 드러낸다. 현재 smoke는 기능 검사이며 이 성능 비교를 대신하지 않는다.

현재 목표는 위 경계와 검증을 단단히 만드는 것이다. 최초 설계와 과거 예제는 [design-original.md](design-original.md), 실제 검사 기록은 [verification.md](verification.md)에 보존한다.
