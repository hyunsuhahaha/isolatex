# 짧은 로컬 실험 기록 — 2026-10-24

목적은 비교 도구와 장애 경계를 확인하는 것이다. 운영 성능 보장이나 일반적인 개선율을 주장하는 결과가 아니다. 방법과 제약은 [실험 가이드](../../docs/experiments.md)에 있다.

환경: WSL2 Ubuntu Linux amd64, Go 1.27.3, 논리 CPU 12, GOMAXPROCS 12. 비교군별 앱 4개·실행 예산 4·대기 예산 8을 생성한 설정에서 확인했다. 초기 지연·GET 크래시 두 시나리오는 같은 앱/런타임 빌드를 사용했고 실행 파일 SHA-256은 JSON에 기록했다. 실험과 그 안의 trial은 순서대로 실행했다. 아래 명령은 당시 실행 기록이며 현재 크래시 도구는 POST를 사용한다.

```sh
bin/compare -warmup 1s -baseline 2s -fault 3s -recovery 2s -repeats 3 -scenario delay -out .tools/compare-linux-delay.json
bin/compare -warmup 1s -baseline 2s -fault 3s -recovery 2s -repeats 3 -scenario crash -out .tools/compare-linux-crash.json
```

각 시나리오에서 순서를 섞은 A/B/C를 세 번씩, 합계 9 trial 실행했다. 각 역할은 초당 40개를 목표로 전송했다. 모든 단계에서 생성 누락은 0이었고 `scheduled = sent + generator_missed`, `sent = HTTP 응답 수 + transport_errors`를 확인했다. 준비 중에도 통계를 기록했지만 아래 표는 장애 단계만 나타낸다.

## 1s 지연 주입

| 비교군 | 반복별 보호 요청 성공 수 / 120 | 성공 응답 P95 범위 |

| A: 예산·프로세스 공유 | 9, 6, 9 | 83.18–94.19ms |
| B: 예산 분리·프로세스 공유 | 12, 11, 11 | 1091.68–1093.28ms |
| C: 예산·프로세스 분리 | 120, 120, 120 | 6.34–6.65ms |

원자료: [2026-10-24-linux-delay-short.json](2026-10-24-linux-delay-short.json).

C에서는 이번 짧은 지연 부하가 보호 영역의 용량을 소모하지 않았다. A/B는 다수 요청을 거절했으므로 성공 요청 P95만으로 비교해서는 안 된다. B는 정상 단계부터 성공 P95 약 11.8ms로 A/C의 약 6.3–6.5ms보다 높았다. 공유 upstream에 대한 그룹별 독립 선택이 같은 프로세스의 내부 슬롯에서 경합할 수 있으므로 B가 한도 분리의 순수한 효과만 보여준다고 해석하지 않는다. 이 실험은 요청 예산만 나눠도 공유 서버의 작업 슬롯까지 예약되는 것은 아니라는 점을 보여준다.

## 초기 GET 크래시 주입 기록

아래 원자료는 자동 재전송 가능성을 통제하지 않은 초기 GET 주입으로 생성됐다. 이후 연결이 응답 없이 닫힐 때 단일 GET 주입이 두 번 실행되는 경로를 회귀 검사로 확인해 POST로 수정했다. 초기 JSON은 보존하지만 초당 정확히 한 번의 서버 실행을 보장하는 기록으로 해석하지 않는다. 현재 도구는 `load_contract.crash_method: POST`를 기록한다.

| 비교군 | 반복별 보호 요청 성공 수 / 120 | 성공 응답 P95 범위 | 보호 영역 PID 유지 |
| --- | --- | --- | --- |
| A: 예산·프로세스 공유 | 100, 92, 100 | 6.31–6.74ms | 세 번 모두 변경 |
| B: 예산 분리·프로세스 공유 | 98, 103, 98 | 11.87–11.96ms | 세 번 모두 변경 |

원자료: [2026-10-24-linux-crash-short.json](2026-10-24-linux-crash-short.json).

공유한 앱 프로세스의 종료가 A/B의 보호 영역에도 영향을 줬다. C에서는 이번 세 번의 trial 동안 보호 전용 프로세스와 보호 요청 성공이 유지됐다. 두 시나리오의 C에서 장애 단계 보호 요청은 각각 360/360 성공했다.

표의 P95는 반복별 성공 표본에서 계산한 범위이며 P95를 합쳐 만든 통계가 아니다. 표본과 측정 시간이 작고 호스트는 개발 머신이다. 더 긴 측정, 더 많은 반복, 별도의 부하 생성 호스트, 공유 upstream 선택 정책의 통제가 필요하다. CPU 고갈·메모리 고갈·DB 락·취소 무시 작업은 이번 원자료에 포함하지 않았다.

## POST 크래시 주입 재검증

같은 OS·Go·CPU 환경에서 수정된 도구로 준비 1s·정상 2s·장애 3s·회복 2s, 역할별 40rps, 세 번 반복을 다시 실행했다. 이번 9 trial은 같은 앱·런타임 실행 파일을 사용하며 SHA-256은 [2026-10-24-linux-crash-post-short.json](2026-10-24-linux-crash-post-short.json)에 있다. 초기 GET 실험과는 다른 실행이며 결과를 합산하지 않는다.

| --- | --- | --- | --- | --- |

| C: 예산·프로세스 분리 | 120, 120, 120 | 6.11–6.18ms | 세 번 모두 유지 | 2, 2, 2 |

모든 단계에서 생성 누락 0과 요청 회계 등식을 확인했다. 모든 trial에서 장애 대상 풀의 재시작 증가를 관측했다. 초당 한 번 크래시 요청을 예약해도 포화·연결 실패·이미 재시작 중인 워커 때문에 실제 재시작 수와 같지는 않다. C의 보호 성공 360/360과 PID 유지도 이 짧은 조건에서의 관측이며 운영 성능 보장으로 일반화하지 않는다. B의 독립 선택 상태라는 기존 해석 제약은 그대로다.

## Windows CPU 집행 진단 원자료

[2026-10-30-windows-cpu-enforcement.json](2026-10-30-windows-cpu-enforcement.json)은 `scripts/check-cpu-windows.ps1 -Count 3`의 summary 원본이다. 소스 e2b0b3ee7567c71def370df014cbfe231d80ab9c의 clean checkout, Go 1.27.3 windows/amd64, Windows build 26200.9711, 논리 CPU 12개에서 세 모드를 각각 3회 실행했다. Go 빌드 환경과 소스 fingerprint, 부모·자손 계수, Job CPU 시간과 실제 계산량을 포함한다. 모든 trial이 통과했다.

이 결과는 위 A/B/C 요청 지연 실험과 다른 schema_version=1 진단 기록이다. CPU cycle을 시간·처리량으로 환산하지 않으며 성공한 짧은 검사 하나로 집행을 항상 보장하지 않는다. 같은 호스트에서 앞서 관측한 CPU 상한 실패의 원인은 아직 미확정이다. [CPU 운영 진단](../../docs/cpu-limits.md#windows-반복-진단-원자료)과 [실패·성공 검증 기록](../../docs/verification.md)을 함께 읽는다. events.jsonl/stderr.log 전체 원자료는 실행 디렉터리에 남으며 이 저장소에는 환경과 계수를 확인한 summary만 보관한다.
